# ASCT 归档报错修复与周期分析

日期：2026-09-01

## 结论

1. 正式回放的 `invalid stem encoding: root mismatch` 已定位并修复。
2. 当前热读命中率低，主要原因确实是 `262,144,000 ops/ring` 的归档周期过短。
3. 周期只提高到 `2x` 不够；按当前“读不续期、写才续期”的实现，要让失败点附近最近窗口达到约 90%，模拟结果需要 `8x`，即 `2,097,152,000 ops/ring`。
4. `8x` 会明显增加 active 数据：2B 操作检查点约 65.44% 的现存 stem 仍为 active。它能改善命中率，但会削弱存储收益。
5. 当前实现中的“热”实际更接近“最近被写过”，不是“最近或频繁被读过”。这是命中率和存储目标难以同时满足的策略问题，不能只靠继续拉长周期解决。

## 报错根因

失败位置约为第 `2,109,396,001` 次操作，错误为：

```text
batch 527350 get: archive: invalid stem encoding:
root mismatch for 06713dd340d0eb6b2ddc3b0a621090e9bd0ca0c327a49974d10ccdbc7dfa50
```

同一个 stem 同时残留了两个归档 membership：

- 根节点 stub 中是当前 valueRef；
- 更深的 edge bucket 中是旧 valueRef。

读取路径先遍历 child，再检查当前节点 stub，因此深层旧 valueRef 遮蔽了当前 valueRef，最终触发 flat stem root 校验失败。

根因是 `absorbArchiveItemsIntoBucket` 在 bucket 已满时直接返回，导致同键的新 valueRef 也无法进入去重替换流程。

修复后：

- 满桶仍可吸收已有键的新版本；
- 只替换 valueRef，不增加 bucket count；
- 真正的新键仍留在 remaining，不会突破 bucket 上限。

旧失败 DB 保持原样，仅作为故障证据，不做就地修复、压缩或覆盖。

## 回归验证

精确复现原始错误模式的测试：

```text
TestStemArchiveFullBucketDuplicateUsesCurrentFlatRoot
```

底层满桶去重测试：

```text
TestFullBucketAbsorbsDuplicateWithoutTakingNewKey
```

定向报错、解析和周期边界测试连续运行 10 次通过；归档/Stem 相关回归集合连续运行 10 次通过；排除显式 Stress/Trace 入口后的 `trie/archive` 包测试通过。

## 周期模拟口径

- 输入：10 个完整 trace 文件，共 `20,242,112,513` 次操作。
- 顺序：严格按 trace 中的操作顺序，不按区块重放。
- batch：4,000 ops。
- shard depth：16，共 65,536 shards。
- 候选周期：`1x / 2x / 4x / 8x`。
- read/touch：只读，不刷新 outer stem epoch。
- write/create：整个 stem 变热并重置 epoch。
- 有效 delete：stem 仍存在时重置整个 stem epoch；最后一个 suffix 删除后 stem 消失。
- missing read 不进入热读命中率分母。
- 模拟器只读 trace，不创建真实 trie，不修改失败 DB。

1B 模拟中，`1x` 累计热读命中率为 90.35%；正式回放前 1B 为 91.27%。

到原失败操作位置，`1x` 模拟累计热读命中率为 80.98%；正式回放为 81.43%。最近完整 100M 模拟为 70.37%，也与正式回放约 68%-70% 的窗口结果一致。因此模拟器足以用于判断周期趋势。

## 2.109B 操作结果

| Prune 周期 | 每轮操作数 | 累计热读命中率 | 最近完整 100M | 2B active stem 占比 |
|---|---:|---:|---:|---:|
| 1x | 262,144,000 | 80.98% | 70.37% | 13.88% |
| 2x | 524,288,000 | 87.38% | 74.32% | 22.83% |
| 4x | 1,048,576,000 | 91.47% | 82.46% | 39.52% |
| 8x | 2,097,152,000 | 95.29% | 90.42% | 65.44% |

最后不足 100M 的 `2.100B-2.109396001B` 窗口中，命中率分别为：

| 周期 | 热读命中率 |
|---|---:|
| 1x | 65.30% |
| 2x | 70.06% |
| 4x | 80.88% |
| 8x | 90.03% |

active stem 占比只是 active tree 保留量的相对代理，不是实际磁盘字节。精确 active storage 必须通过真实回放统计，并继续排除 archive 数据目录和归档节点字节。

## 建议

### 正确性

保留当前满桶重复键修复。下一次正式回放必须从新 DB 开始，不能复用已含重复 membership 的失败 DB。

### 周期

下一轮真实实验应优先验证 `4x` 和 `8x`：

- `4x` 用于观察较强存储优化下的性能和命中率；
- `8x` 用于验证约 90% 最近窗口命中率目标及其 active storage 代价；
- `2x` 已被模拟证据基本排除，不能解决后段命中率问题。

如果必须先选单一候选，选择 `8x` 作为“命中率目标验证组”，但不能把它直接视为最终配置。

### 热度语义

当前 `StemTrie.Get` 明确不会激活 archived stem，`Shard.Get` 也不会更新 epoch。只读但频繁访问的数据会持续留在冷层。因此：

- 单纯拉长周期会用更多 active storage 换命中率；
- 若产品目标中的“热数据”包含读热数据，需要单独设计低写放大的读热追踪/晋升策略；
- 不能在普通 Get 中直接把每次读取变成持久化 epoch 写入，否则会把读放大成写，破坏性能比较口径。

正式重跑前，应先确定是继续采用“写热”定义，还是把“读热”纳入归档保留策略。这个语义选择会直接决定最终周期和存储上限。

## 资源评估

- 10M 模拟：约 5.15 秒，峰值 RSS 约 295 MiB。
- 100M 模拟：约 47.9 秒，峰值 RSS 约 294 MiB。
- 1B 模拟：约 7 分 29 秒，峰值 RSS 约 1.54 GiB。
- 2.109B 模拟：约 16 分 53 秒，峰值 RSS 约 4.28 GiB。

状态内存随唯一 stem 数增长，不能把 2.109B 的吞吐和内存简单线性外推到完整 20.2B。完整周期模拟应先增加可恢复的分段状态或更紧凑的状态表示，再运行全量。
