# AMT V16 candidate: hot-tree hash and encode work

V16 starts from the frozen V15 source tag `amt-v15-source` at
`64b9eacdf581ab8a39a3e870347486515bc384d3`. The candidate runtime code
is committed at `441e3a01d513b416dcaf6b210695003c0409d422` on
`codex/amt-v16-tree-opt-20261123`. It changes only the `hx` tree:

- Hashing and committing copied nodes share immutable stub lists instead of
  allocating duplicate slices. Stub mutation paths already use copy on write.
- Short-node encoding reads the leaf flag directly from the compact key's
  first byte rather than unpacking the entire key to choose epoch versus
  subtree aggregate metadata.

The RLP format, epoch/stub content, ECMH, one-bit bucket routing, pruning
schedule, and external interfaces are unchanged. The V14 and V15 source tags
have not moved.

## Verification

Local `go test ./trie/archive/mpt/... ./trie/archive/cuckoo -count=1` passed.
The MPT server ran the same tests and compiled a test binary for each screen
variant. All four uninstrumented strict-block replays passed on the first
100 windows (blocks 46,147–2,012,146; 164,936,392 operations). Each ended
with 105,153 buckets, 991,589 hot leaves, and root
`0x0271a4fb1515240a42c477469a762682f4b3cf24086260629eac4c980a46d6f9`.
Window boundaries, operation counts, and staged hot-node bytes were identical
across the variants. The replay retained one prune per block, full
redemption-bucket auditing, 8 bucket workers × 2 item workers,
`FullBucketsBeforeSplit=2`, and `MPT_OP_TRACE` off.

| 100-window screen, seconds | V15 baseline 1 | Hash-copy only | V16 combined | V15 baseline 2 |
| --- | ---: | ---: | ---: | ---: |
| Parse | 119.331 | 113.604 | 113.548 | 113.432 |
| State operations | 192.970 | 192.537 | 192.819 | 193.584 |
| `Commit_Hx` (hot-tree hash/commit) | 94.925 | 93.896 | **92.813** | 95.033 |
| Counted commit and DB write, excluding verification | 118.895 | 118.000 | **116.866** | 119.059 |

The combined candidate reduced `Commit_Hx` by 2.2–2.3% versus the two V15
baselines; 74 and 76 of 100 paired windows improved, respectively. Staging
and trie-DB commit time were essentially unchanged. Block time was 0.67%
below the immediately following baseline, but the first baseline had 5.8
more seconds of Parse time than the other runs. State operations and pruning
did not show a consistent improvement. These screens establish a local
hot-tree commit benefit, not a full-trace throughput claim.

On Windows, Go 1.26.0, AMD Ryzen 9 3900X, the fixed 16-stub dirty-branch
hash benchmark fell from about 1,017 to 712 B/op and from 10 to 6
allocations/op; latency moved from about 3.18 to 3.03 µs/op. The leaf
short-node encoding benchmark fell from about 208 to 139 ns/op, 160 to
80 B/op, and 2 to 1 allocations/op. A 262,144-key in-memory write
benchmark showed `hx` and native MPT both around 1.2 µs/op; it does not
explain the later full-replay operations gap.

A separate CPU-profile run of the unchanged V15 source and a native MPT
run covered the same first 100 windows. The profiles include all replay
work and use different harnesses, so inclusive function times are
diagnostic, not additive or a causal estimate. They motivated the hash
and encoding probes; the exact per-window timings above come from the
uninstrumented A/B.

The commands, patch SHA-256 values, binary SHA-256 values, logs, metadata,
CSVs, summaries, and profiles are retained under
`AMT实验结果/v16_tree_hashcopy_20261123/` in the paper workspace and under
`/root/asct_codex/results/trace_stress/V16_hashcopy_screen_20261123/` on
the MPT server. The screened binary contains the same runtime changes as
the source commit; the commit additionally includes benchmark tests and
comments.

## Promotion gate

V15 itself has only a 60-window screen and no 507-window full replay.
V16 therefore remains a candidate. Do not assign it the formal `amt-v16`
tag or use these first-100-window numbers as paper-wide performance data.
A full strict-block replay from a fresh database, and comparison against
a same-server V15 full baseline, are required before claiming a full-run
improvement. No historical archive database was modified.
