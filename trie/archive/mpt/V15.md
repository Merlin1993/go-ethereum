# V15 candidate: one-bit overflow routing

This candidate starts from the completed `amt-v14` source at `a77a2733569456f1fc2e30acfc1f02aa54ec5d14`. It changes the placement of **newly extracted** archive entries after two full buckets at a logical prefix: the next bucket goes one bit deeper. It never splits existing bucket payloads. The initial logical prefix remains `ceil(D/4)*4` bits, and the bucket capacity, filter, ECMH commitment, redemption, and full-audit rules are unchanged.

The bucket identifier now stores a two-byte bit depth and a packed prefix before its eight-byte sequence number. A hexary stub mounts at the complete-nibble part; lookup checks the full logical bit prefix before probing the filter. This format requires a fresh archive database. The `amt-v14` tag and its full-replay database remain the V14 baseline.

The isolated V10-based one-bit experiment (`18db3b891`) completed the strict-block 507-window trace on Verkle with 2,816,724 final buckets. Its query-normalized false-positive event rate was about half of the original V11 run. Those figures describe the experimental source, **not** this V14-based candidate; they must not be reused as its measured performance.

V14's parallel bucket creation, batched commitment append, flat filter storage, stub refresh, and pruning optimizations remain in the code. Consecutive extracted entries with the same bit-level destination are batched conservatively; a test compares batch and singleton routing roots on both hashdb and pathdb.

Local fixed-100-entry prune microbenchmark on AMD Ryzen 9 3900X, Windows, Go 1.26.0 (`-benchtime=20x -count=2`):

| Operation | V14 | Candidate |
| --- | ---: | ---: |
| Create/route 100 entries | 1.83–1.95 ms | 1.84–1.86 ms |
| Top up 50 entries | 1.02–1.04 ms | 1.00–1.02 ms |

The first direct per-entry port took 9.4–9.5 ms for 100 entries; it was replaced by the batched implementation before this candidate. This synthetic benchmark does not establish full-trace throughput or final bucket distribution.
